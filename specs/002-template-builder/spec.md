# Feature Specification: Template Builder

**Feature Branch**: `002-template-builder`  
**Created**: 2026-02-21  
**Status**: Draft  
**Input**: User description: "Create resume and cover letter templates via a drag-and-drop interface with data-bound elements, formatting controls, looping mechanisms, variable substitution, and PDF preview"

## Clarifications

### Session 2026-02-21

- Q: Can loop containers be nested (e.g., a skills loop inside a work history loop)? → A: Single-level nesting only; loops contain flat sub-elements, no nested loops.
- Q: Should the second built-in template be called "Contemporary" or "Modern"? → A: "Modern" -- matches existing codebase naming.
- Q: Should page margins be configurable per template? → A: Yes, per-template configurable margins (top, bottom, left, right).
- Q: Should the system ship with built-in cover letter templates? → A: Yes, two built-in cover letter templates (formal and casual styles) with generic placeholder content.
- Q: How should templates be handled in backup/restore? → A: Both -- included in full backup/restore AND individually exportable/importable per template.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build a Resume Template from Scratch (Priority: P1)

A user opens the template builder, creates a new resume template, and constructs it by dragging elements onto a canvas. They add a profile header block, a horizontal rule, a professional summary section, a work history loop (each entry showing job title, employer, dates, summary paragraph, and bullet points), a skills section grouped by category, education entries, and certifications. They configure formatting for each block -- font sizes, bold/italic styles, alignment, spacing, bullet character style, and separator characters. They save the template and it becomes available for use in the Export page.

**Why this priority**: This is the core value proposition. Without the ability to create resume templates visually, the entire feature has no purpose. It replaces the current hardcoded template system and enables unlimited customization.

**Independent Test**: Can be fully tested by creating a template in the builder, then exporting a resume using that template and verifying the PDF output matches the configured layout.

**Acceptance Scenarios**:

1. **Given** the user is on the template builder page, **When** they create a new resume template, **Then** they see an empty canvas with a palette of available element blocks.
2. **Given** an empty template canvas, **When** the user drags a "Profile Header" element onto it, **Then** the element appears on the canvas showing a placeholder representation and configurable properties (alignment, font size, separator character).
3. **Given** a template with multiple elements, **When** the user drags an element to a new position, **Then** the element order updates and the canvas reflects the new arrangement.
4. **Given** a template with a "Work History Loop" element, **When** the user adds sub-elements inside the loop (job title, employer, date range, summary, bullets), **Then** each sub-element is configurable independently and the loop indicates it will repeat for each work history entry.
5. **Given** a completed template layout, **When** the user saves the template with a name, **Then** the template is persisted and appears in the template selection list on the Export page.
6. **Given** a saved user-created template, **When** the user exports a resume using it, **Then** the generated PDF renders all elements in the configured order with the specified formatting.

### User Story 2 - Reproduce Existing Templates (Priority: P1)

The system ships with two built-in template configurations ("Professional" and "Modern") that reproduce the output of the current hardcoded templates exactly. These serve as reference examples and as working defaults so users can export resumes immediately. Users can duplicate a built-in template to use as a starting point for customization.

**Why this priority**: Equal to P1 because existing functionality must not regress. Users who rely on the current Professional and Modern templates must continue to get identical output. These also serve as proof that the builder is expressive enough to handle real-world templates.

**Independent Test**: Export a resume using the built-in "Professional" configuration and compare the PDF output to one generated by the current hardcoded template -- they must be visually identical.

**Acceptance Scenarios**:

1. **Given** the template list, **When** the user views available templates, **Then** "Professional" and "Modern" appear as built-in templates that cannot be deleted.
2. **Given** the "Professional" built-in template, **When** the user exports a resume with the same data selections, **Then** the PDF output is visually identical to the current hardcoded Professional template (centered header, pipe separators, underlined section headings, standard bullet characters).
3. **Given** the "Modern" built-in template, **When** the user exports a resume with the same data selections, **Then** the PDF output is visually identical to the current hardcoded Modern template (left-aligned header, middle-dot separators, no heading underlines, larger name font).
4. **Given** a built-in template, **When** the user clicks "Duplicate", **Then** a copy is created that they can freely edit without affecting the original.

---

### User Story 3 - Configure Element Formatting (Priority: P2)

When a user selects any element on the template canvas, a properties panel appears allowing them to configure formatting options specific to that element type. Common options include font size, bold/italic/regular style, text alignment (left, center, right), and vertical spacing (before/after). Certain elements have type-specific options: separator characters for profile links, bullet characters for bullet lists, heading underline toggle for section headings, and date format preferences for date fields.

**Why this priority**: Formatting control is what makes templates distinct from each other. Without it, all templates would look identical. However, a basic version of the builder could work with sensible defaults, making this P2.

**Independent Test**: Can be tested by creating a template, modifying formatting properties on several elements, exporting a PDF, and verifying the formatting appears correctly.

**Acceptance Scenarios**:

1. **Given** a selected element on the canvas, **When** the user views the properties panel, **Then** they see formatting options appropriate to that element type.
2. **Given** a section heading element, **When** the user toggles "Underline" on and sets font size to 14, **Then** the canvas preview updates to reflect these changes.
3. **Given** a profile links element, **When** the user changes the separator from "|" to "~", **Then** the exported PDF shows profile links separated by the chosen character.
4. **Given** a bullet list element, **When** the user selects a different bullet character (dash, circle, square, arrow), **Then** the exported PDF uses that bullet character.

### User Story 4 - Build a Cover Letter Template (Priority: P2)

A user creates a cover letter template that includes a profile header, a date, and body text blocks. Within the body text, they can insert template variables like `{{company_name}}` and `{{position_title}}` that will be automatically substituted when the cover letter is generated for a specific job application. They can also insert guided prompt placeholders like `{{prompt: Explain why you want to work for this company}}` -- when generating a cover letter from this template, the user is presented with each prompt and fills in their response, which is then inserted into the final document.

**Why this priority**: Cover letter templates are a stated requirement but secondary to resume templates. The resume builder infrastructure (drag-and-drop, element system, formatting) must exist first, and cover letter templates build on top of it.

**Independent Test**: Can be tested by creating a cover letter template with variables and prompts, generating a cover letter for a job application, filling in the prompts, and verifying the final PDF contains the substituted values and user-provided text.

**Acceptance Scenarios**:

1. **Given** the template builder, **When** the user creates a new cover letter template, **Then** the available element palette shows cover-letter-specific elements (body text block, variable insertion, guided prompt placeholder, date, greeting, closing).
2. **Given** the cover letter template list, **When** the user views available templates, **Then** "Formal" and "Casual" appear as built-in cover letter templates that cannot be deleted.
3. **Given** a cover letter template with `{{company_name}}` and `{{position_title}}` variables, **When** the user generates a cover letter for a job application, **Then** those variables are automatically replaced with the application's company name and position title.
4. **Given** a cover letter template with a `{{prompt: Why do you want this role?}}` placeholder, **When** the user generates a cover letter, **Then** they are presented with the prompt text and a text area to write their response before the PDF is generated.
5. **Given** a cover letter template, **When** the user generates it without selecting a job application, **Then** they are prompted to manually enter values for `{{company_name}}` and `{{position_title}}`.

### User Story 5 - Work History Looping (Priority: P2)

When building a template, the user can add a "Work History Loop" container element. Inside this container, they arrange sub-elements that define how each individual work history entry is rendered -- job title, employer name, date range, summary paragraph, primary bullets, and outcome/secondary bullets. At export time, the system iterates over each selected work history entry and renders the sub-element layout for each one. A similar looping mechanism is available for other repeating data types: skills by category, education entries, certifications, and profile links.

**Why this priority**: Looping is essential for any real resume template since work history, skills, education, and certifications are all lists. Without it, the builder cannot produce functional resumes. However, the basic element system must exist first.

**Independent Test**: Can be tested by creating a template with a work history loop containing title, employer, and bullet sub-elements, selecting 3 work history entries at export, and verifying all 3 render in the PDF with the configured sub-element layout.

**Acceptance Scenarios**:

1. **Given** a template canvas, **When** the user drags a "Work History Loop" onto it, **Then** a container element appears that accepts sub-elements to be dragged inside it.
2. **Given** a work history loop with sub-elements (title, employer, dates, bullets), **When** the user exports with 4 work history entries selected, **Then** the PDF renders all 4 entries with the same sub-element layout.
3. **Given** a skills loop element, **When** configured to group by category, **Then** at export time skills are rendered grouped under their category names.
4. **Given** a loop element with no data at export time (e.g., no certifications selected), **When** the PDF is generated, **Then** the loop and its section heading are omitted entirely.

---

### User Story 6 - Preview PDF Output (Priority: P3)

While building or after saving a template, the user can click a "Preview" button that generates a PDF using sample data (or their actual profile data and a selected lens) and opens it for viewing. This provides a rapid feedback loop so users can see how their template will look as a finished document without going through the full export workflow.

**Why this priority**: Preview is a convenience feature that accelerates the design process. Users can still test their templates by going through the normal export flow, but preview removes friction. It is not required for the builder to be functional.

**Independent Test**: Can be tested by building a template, clicking Preview, and confirming a PDF opens that reflects the current template configuration.

**Acceptance Scenarios**:

1. **Given** a template with at least one element, **When** the user clicks "Preview", **Then** a PDF is generated using their profile data and the most recent lens selections (or sample data if none exist) and opened for viewing.
2. **Given** the user modifies an element's formatting and clicks Preview again, **Then** the regenerated PDF reflects the updated formatting.
3. **Given** a cover letter template with variables, **When** the user clicks Preview, **Then** variables are shown with placeholder text (e.g., "[Company Name]") rather than blank spaces.

---

### User Story 7 - Manage Templates (Priority: P3)

Users can view all their templates in a list, rename them, duplicate them, and delete user-created templates. Built-in templates (Professional, Modern) cannot be deleted but can be duplicated. Each template indicates whether it is a resume template or a cover letter template.

**Why this priority**: Basic CRUD operations for templates. The builder needs at minimum create and save (covered in P1); rename, duplicate, and delete are quality-of-life features.

**Independent Test**: Can be tested by creating several templates, renaming one, duplicating another, deleting a third, and verifying the list updates correctly.

**Acceptance Scenarios**:

1. **Given** the template list, **When** the user views it, **Then** each template shows its name, type (resume/cover letter), and whether it is built-in or user-created.
2. **Given** a user-created template, **When** the user deletes it, **Then** it is removed from the list and no longer available for export.
3. **Given** a user-created template, **When** the user renames it, **Then** the new name is reflected everywhere the template appears.
4. **Given** a built-in template, **When** the user attempts to delete it, **Then** the delete option is not available.

---

### Edge Cases

- What happens when a user tries to export with a template that references element types the data doesn't support (e.g., a certifications section when no certifications exist)? Sections with no data are silently omitted from the PDF.
- How does the system handle a template saved with an older version of the element schema after new element types are added? Templates are forward-compatible; unknown element types are skipped with a warning.
- What happens if a user deletes a template that is referenced by an existing export record? The export record retains the template name as a snapshot but the template is no longer available for new exports.
- What happens when a cover letter template variable references a field that doesn't exist on the job application (e.g., application has no position title)? The variable is replaced with an empty string and a warning is shown to the user before generation.
- What happens when a loop contains no sub-elements? The loop is treated as empty and omitted from output, with a warning shown in the builder.
- What happens when the user drags an element that is incompatible with the template type (e.g., a work history loop into a cover letter template)? The drop is rejected with a visual indicator explaining why.

## Requirements *(mandatory)*

### Functional Requirements

#### Template Management
- **FR-001**: System MUST allow users to create new resume templates with a user-provided name.
- **FR-002**: System MUST allow users to create new cover letter templates with a user-provided name.
- **FR-003**: System MUST ship with two built-in resume template configurations ("Professional" and "Modern") that produce output identical to the current hardcoded templates.
- **FR-003a**: System MUST ship with two built-in cover letter template configurations: a "Formal" template (profile header, date, recipient address block, greeting, structured body paragraphs with variable placeholders, formal closing) and a "Casual" template (profile header, greeting, conversational body with variable placeholders, informal closing). Both use generic placeholder content and include `{{company_name}}`, `{{position_title}}`, and guided prompt placeholders.
- **FR-004**: System MUST allow users to duplicate any template (built-in or user-created) to create an editable copy.
- **FR-005**: System MUST allow users to rename user-created templates.
- **FR-006**: System MUST allow users to delete user-created templates.
- **FR-007**: System MUST prevent deletion of built-in templates.
- **FR-008**: System MUST persist all template configurations so they survive application restarts.

#### Template Builder Canvas
- **FR-009**: System MUST provide a drag-and-drop canvas where users arrange elements vertically to define template layout.
- **FR-010**: System MUST provide an element palette listing all available element types, organized by category (formatting, data-bound, containers).
- **FR-011**: Users MUST be able to reorder elements on the canvas via drag-and-drop.
- **FR-012**: Users MUST be able to remove elements from the canvas.
- **FR-013**: System MUST provide a properties panel that displays configurable options when an element is selected on the canvas.
- **FR-014**: System MUST increase the default application window size globally to accommodate the builder's three-panel layout (palette, canvas, properties), affecting all pages.

#### Resume Element Types
- **FR-015**: System MUST support a "Profile Header" element that renders the user's name, contact information, and profile links with configurable alignment (left/center), font sizes, and separator characters.
- **FR-016**: System MUST support a "Role Descriptors" element that renders role descriptor labels with a configurable separator character and text style.
- **FR-017**: System MUST support a "Professional Summary" element that renders one or more professional summaries, with the master summary as a paragraph and additional summaries as bullet points.
- **FR-018**: System MUST support a "Work History Loop" container element that repeats its sub-elements for each selected work history entry.
- **FR-019**: Within a Work History Loop, system MUST support sub-elements for: job title, employer name, date range, summary paragraph, primary bullet list, and secondary/outcome bullet list.
- **FR-020**: System MUST support a "Skills" element that renders skills grouped by category with configurable grouping display (category label + colon + comma-separated skills).
- **FR-021**: System MUST support an "Education Loop" container element that repeats for each selected academic credential with sub-elements for credential type, field of study, institution, and completion date.
- **FR-022**: System MUST support a "Certifications Loop" container element that repeats for each selected certification with sub-elements for name, issuing body, and dates.
- **FR-023**: System MUST support a "Core Expertise" element that renders core expertise labels with a configurable separator.
- **FR-024**: System MUST support a "Horizontal Rule" formatting element with configurable line weight.
- **FR-025**: System MUST support a "Section Heading" formatting element with configurable text, font size, bold/uppercase toggles, and optional underline rule.
- **FR-026**: System MUST support a "Spacer" formatting element with configurable height.
- **FR-027**: System MUST support a "Static Text" element that renders a hardcoded user-provided string with configurable font size, style (bold/italic/regular), and alignment.

#### Element Formatting Properties
- **FR-028**: All text-bearing elements MUST support configurable font size.
- **FR-029**: All text-bearing elements MUST support configurable text style (regular, bold, italic, bold-italic).
- **FR-030**: All text-bearing elements MUST support configurable text alignment (left, center, right).
- **FR-031**: All elements MUST support configurable vertical spacing (space before and space after, in points).
- **FR-032**: Bullet list elements MUST support configurable bullet character (filled circle, dash, arrow, square, open circle).
- **FR-033**: Elements that display lists inline (profile links, role descriptors, core expertise) MUST support configurable separator characters.
- **FR-033a**: Each template MUST support configurable page margins (top, bottom, left, right) with sensible defaults matching current values (1 inch sides, 0.75 inch top/bottom).

#### Cover Letter Element Types
- **FR-034**: Cover letter templates MUST support a "Body Text" element that accepts rich text with variable placeholders.
- **FR-035**: Cover letter templates MUST support template variables (`{{company_name}}`, `{{position_title}}`) that are automatically substituted from job application data at generation time.
- **FR-036**: Cover letter templates MUST support guided prompt placeholders (`{{prompt: descriptive text}}`) that present the user with a text input at generation time, and the user's response is inserted into the final document.
- **FR-037**: Cover letter templates MUST support a "Date" element that renders the current date or a user-specified date with configurable format.
- **FR-038**: Cover letter templates MUST support a "Greeting" element (e.g., "Dear Hiring Manager,") with configurable text and optional variable substitution.
- **FR-039**: Cover letter templates MUST support a "Closing" element (e.g., "Sincerely,") with configurable text followed by the user's name.
- **FR-039a**: Cover letter templates MUST support a "Recipient Address Block" element for formal letters, rendering configurable fields (recipient name, company name, company address) with variable substitution support.
- **FR-040**: When generating a cover letter without a linked job application, system MUST prompt the user to manually provide values for all template variables.

#### Looping and Containers
- **FR-041**: Loop container elements MUST accept sub-elements that define the layout of each repeated item.
- **FR-042**: Loop elements MUST render nothing (including their section heading) when no data items are selected for that loop at export time.
- **FR-043**: Sub-elements within a loop MUST support the same formatting options as top-level elements.
- **FR-044**: System MUST support configurable spacing between loop iterations (gap between work history entries, education entries, etc.).
- **FR-045a**: Loop containers MUST support only single-level nesting: loops contain flat sub-elements and MUST NOT accept other loop containers as children.

#### PDF Generation and Preview
- **FR-045**: System MUST generate PDFs from user-created templates that faithfully reproduce the configured element layout, order, and formatting.
- **FR-046**: System MUST provide a "Preview" function that generates a PDF using the current template configuration and the user's actual data (or sample placeholders if no data exists).
- **FR-047**: User-created templates MUST be selectable on the existing Export page alongside built-in templates.
- **FR-048**: Cover letter templates MUST be selectable when exporting a cover letter, replacing the current single-format export.

#### Backward Compatibility
- **FR-049**: The existing Export page workflow (select template, select content, generate) MUST continue to function with both built-in and user-created templates.
- **FR-050**: Existing export records that reference the old "professional" or "modern" template IDs MUST continue to display correctly in export history.

#### Data Portability
- **FR-051**: User-created templates MUST be included in the existing full data backup/restore mechanism alongside all other user data.
- **FR-052**: System MUST allow individual templates to be exported as standalone files and imported back, enabling template sharing or transfer between installations.

### Key Entities

- **Template**: A named, typed (resume or cover letter) configuration that defines a document layout. Has a name, type, a flag indicating whether it is built-in, page margins (top, bottom, left, right), and an ordered list of elements. Belongs to the user's local data.
- **Template Element**: A single block within a template layout. Has a type (profile header, work history loop, horizontal rule, static text, etc.), a sort order within its parent, formatting properties (font size, style, alignment, spacing), and type-specific configuration (separator character, bullet character, heading text, etc.). May be a top-level element or a direct child of a loop container (single-level nesting only; no nested loops).
- **Template Variable**: A named placeholder within a cover letter template body that is substituted at generation time. Has a variable key (e.g., "company_name") and a source (job application field or user-provided).
- **Guided Prompt**: A placeholder within a cover letter template that presents the user with a question/instruction at generation time and inserts their free-text response. Has prompt text and an optional default value.

## Assumptions

- **Single-column layout**: Templates use a vertical, single-column flow layout (elements stack top-to-bottom). Multi-column/sidebar layouts are out of scope for this feature. Both existing templates use single-column flow, and this keeps the builder simple while covering the vast majority of professional resume formats.
- **Existing font family**: Templates use the existing Liberation Sans font family (Regular, Bold, Italic, Bold-Italic). Adding additional font families is out of scope for this feature.
- **Page size**: All templates target US Letter (8.5" x 11") page size with per-template configurable margins (defaulting to 1" left/right, 0.75" top/bottom).
- **Cover letter variable auto-fill**: When a cover letter is generated for a specific job application, `{{company_name}}` and `{{position_title}}` are auto-filled from the application record. When generated standalone, the user provides these values manually.
- **No WYSIWYG editing**: The canvas shows a structured block representation of elements (not a pixel-perfect preview). Users rely on the Preview button to see actual PDF output.
- **Template portability**: Templates are stored locally. They are included in the existing full data backup/restore and can also be individually exported/imported as standalone files.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can create a new resume template and generate a PDF from it within 15 minutes on their first attempt.
- **SC-002**: The built-in "Professional" template configuration produces PDF output that is visually indistinguishable from the current hardcoded Professional template.
- **SC-003**: The built-in "Modern" template configuration produces PDF output that is visually indistinguishable from the current hardcoded Modern template.
- **SC-004**: Users can build a template with at least 8 distinct element types (header, heading, rule, summary, work history loop, skills, education, certifications) and all render correctly in the exported PDF.
- **SC-005**: Cover letter templates with variable substitution correctly replace all template variables with job application data or user-provided values in 100% of cases.
- **SC-006**: The Preview function generates and opens a PDF within 5 seconds for a template with typical resume content (5 work history entries, 20 skills, 3 education entries).
- **SC-007**: All existing export workflows continue to function without modification after the template builder is deployed.
- **SC-008**: Users can duplicate a built-in template and modify it to create a visually distinct resume layout within 10 minutes.
